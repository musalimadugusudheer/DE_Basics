Q01
What is Injection/Ingestion in ADF and ADS?
ADF / ADS
Interviewer likely means: "Ingestion" — bringing raw data into the platform — and possibly "parameter injection" (dynamic content in ADF pipelines). ADS = Azure Data Studio or Azure Databricks Service.

Ingestion in ADF (Azure Data Factory):

Ingestion is the first step — pulling data from source systems and landing it in ADLS Gen2 or a Bronze layer. In ADF, we do this using Copy Activity, Data Flows, and Linked Services. In my Kahramaa project, ADF handled ingestion from four source types: Oracle ERP (on-prem via Self-Hosted Integration Runtime), MySQL CRM, SharePoint flat files, and IoT telemetry via Azure Event Hubs. We had about 32 ADF pipelines doing this — each pipeline parameterised so a single template could serve multiple tables.

Parameter Injection in ADF — This is the practice of passing runtime values into pipelines using @pipeline().parameters and @variables() expressions. Instead of hardcoding table names, file paths, or date ranges, we inject them dynamically. For example, our batch ingestion pipeline accepted source_table, watermark_date, and target_container as parameters. One master pipeline looped through a metadata control table and injected these values per table — making it fully metadata-driven.

Ingestion in ADS (Azure Databricks Service):

In Databricks, ingestion happens via Auto Loader for streaming and spark.read for batch. Auto Loader uses cloudFiles format to incrementally ingest files from ADLS Gen2 as they arrive — it tracks what's been processed using checkpoints so there's no duplicate ingestion. For our IoT meter data (2.8M events/day), we used Auto Loader feeding directly into the Bronze Delta table. ADF triggered the Databricks notebooks once ingestion was staged, so the two tools were complementary: ADF for orchestration and movement, Databricks for transformation.

# Auto Loader ingestion in Databricks (ADS) df = (spark.readStream .format("cloudFiles") .option("cloudFiles.format", "json") .option("cloudFiles.schemaLocation", "/mnt/schema/iot_schema") .load("/mnt/landing/iot_events/") ) # Write to Bronze Delta with checkpointing (df.writeStream .format("delta") .option("checkpointLocation", "/mnt/checkpoints/iot_bronze") .outputMode("append") .table("bronze.iot_meter_readings") )

Q03
What is Schema Evolution and How Can You Use It?
Delta Lake

Schema evolution is the ability of a data table to automatically accept and handle structural changes in incoming data — new columns, changed column types, dropped columns — without breaking existing pipelines or requiring manual ALTER TABLE.

Real scenario from Kahramaa: Mid-project, the Oracle ERP team added three new columns to the customer billing table — new_tariff_tier, green_energy_flag, and subsidy_code. Without schema evolution, all pipelines writing to the Silver Delta table would have failed. With mergeSchema = true, the new columns were automatically added to the Delta table and backfilled as NULL for historical records. No pipeline downtime, no manual intervention.

Two modes in Delta Lake:

1
mergeSchema = true — Additive only. New columns in the incoming DataFrame are added to the existing table schema. Existing data gets NULL for the new columns. Safe and non-destructive. Use this for most production scenarios.
2
overwriteSchema = true — Replaces the entire schema. Use only when doing a full reload and you deliberately want to redefine the table structure. Destructive — historical schema is lost. Use with extreme caution.
# mergeSchema — safest option for production df_new.write \ .format("delta") \ .mode("append") \ .option("mergeSchema", "true") \ .saveAsTable("silver.customer_billing") # Auto Loader with schema evolution enabled spark.readStream \ .format("cloudFiles") \ .option("cloudFiles.schemaEvolutionMode", "addNewColumns") \ .option("cloudFiles.inferColumnTypes", "true") \ .load("/mnt/landing/billing/")

Schema drift in ADF Data Flows: ADF has a built-in "Allow schema drift" toggle in the Source transformation. When enabled, columns arriving that aren't in the defined schema are passed through dynamically. This is useful when you don't want to predefine every column in a metadata-driven pipeline. We used this for SharePoint files where the column list changed month to month.

Interview tip: Always mention the governance trade-off — schema evolution is powerful but you must monitor for accidental type changes (e.g., an INT column becoming STRING). We used Great Expectations in our pipeline to validate column types before writes. If a type mismatch was detected, the pipeline raised an alert rather than silently corrupting the table.
Q04
What RCA Can You Use for 100 GB Data and How Do You Distribute a Large Dataset?
Spark / Perf

Root Cause Analysis (RCA) approach for slow / failing 100GB pipeline:

1
Check Spark UI — Stages tab first. Look for stages with dramatically longer runtimes. A 2-minute stage alongside 20-second stages = data skew. Check the Tasks tab — if one task handles 10x more data than others, skew is confirmed.
2
Identify the shuffle. In our Kahramaa project, Zone-A (Doha central district) had 40% of all meter readings. Grouping by zone caused a single task to process 38GB while others processed 2GB. Stage runtime was 38 minutes for that one task. Identified via Spark UI → Stage → Task Metrics → Input Size per task.
3
Check for spill. Spark UI → Executor tab → Disk spill / Memory spill columns. If tasks are writing to disk mid-sort, memory is insufficient for the shuffle. Fix: increase spark.executor.memory, or reduce spark.sql.shuffle.partitions.
4
Check GC time. If GC time > 10% of task time in Executor metrics, memory pressure is the root cause. Increase executor memory or use Tungsten off-heap.
5
Check DAG for unnecessary wide transformations. Lineage tab — are there multiple shuffle stages that could be collapsed? Use cache() to break recomputation chains if a DataFrame is used in 2+ downstream operations.
Kahramaa War Story — Zone-A Skew Fix: Identified skew on zone column. Fixed by salting: appended a random number 0–9 to the zone key during aggregation (e.g., Zone-A_3), aggregated at salted level, then reduced back. Task time dropped from 38 minutes → 4 minutes on the same cluster.
# Salting fix for skewed groupBy from pyspark.sql import functions as F df_salted = df.withColumn( "salted_zone", F.concat(F.col("zone_id"), F.lit("_"), (F.rand() * 10).cast("int")) ) df_agg = df_salted.groupBy("salted_zone").agg(F.sum("consumption_kwh").alias("partial_sum")) df_final = df_agg.withColumn("zone_id", F.split(F.col("salted_zone"), "_")[0]) \ .groupBy("zone_id").agg(F.sum("partial_sum").alias("total_kwh"))

Distributing a Large Dataset (100GB+):

  • Partition wisely: Partition by a high-cardinality column that's used in WHERE clauses — in our case, meter_read_date (date partitioning) and district_code. Never partition by a column with only 2–3 values — that creates large, unbalanced files.
  • Target partition size ~128MB–256MB: For 100GB, aim for ~400–800 partitions. Too few = large tasks; too many = scheduler overhead. Use repartition(n) before write or set spark.sql.shuffle.partitions.
  • Z-ordering in Delta: For query patterns that filter on multiple columns, ZORDER BY (zone_id, read_date) co-locates related data in the same files, reducing data scanned dramatically. Used on our Gold consumption_summary table.
  • Broadcast small dims: Any dimension table under 10MB should be broadcast-joined rather than shuffled. No network shuffle needed — each executor gets a copy.
  • Bucketing for repeated joins: If you repeatedly join a large table to the same key, bucket on that key at write time so joins require zero shuffle.
Q05
Difference Between Clustered and Non-Clustered Index
SQL / DB
AspectClustered IndexNon-Clustered Index
Physical order Rows are physically stored on disk in the index order A separate structure with pointers to the actual rows
Per table limit Only ONE per table (data can only be sorted one way) Multiple allowed — up to 999 in SQL Server
Speed Faster for range queries and ORDER BY on index key Fast for exact lookups; adds a pointer lookup step
Storage No extra storage — IS the data Requires additional storage for the index structure
Best use Primary Key, date ranges, sequential reads Non-PK columns used in WHERE / JOIN conditions
Analogy A book sorted alphabetically — the book IS the index A book's back-index — separate page with page numbers
Kahramaa context: In our Oracle ERP source DB, the meter_reading table had a clustered index on reading_date — since 90% of queries were date-range based (e.g., "fetch all readings for October"). Non-clustered indexes were placed on meter_id and customer_account_no for lookup joins. This reduced ADF Copy Activity extraction time by ~35% compared to a full scan.

Delta Lake equivalent: Delta doesn't use B-tree indexes. Instead, it uses file-level statistics (min/max per column per file) for data skipping — effectively similar to a clustered index where files are physically grouped. ZORDER clustering co-locates data on frequently filtered columns, mimicking a multi-column clustered index in a Lakehouse context.

Architecture & Design Principles
Q06
Thumb Rule for Data Flow from One Source to Another Source
Architecture

The core thumb rules I follow when designing any data flow pipeline:

1
Push filters as early as possible (predicate pushdown). Never pull 10 million rows across the network to filter to 100K at destination. Push the WHERE condition to the source system (Oracle, MySQL) so only relevant data moves. In ADF Copy, use Query mode instead of Table mode to push the filter.
2
Never move data twice if you can transform in-flight. If you're copying from Oracle to ADLS and need to mask PII — do it in the Data Flow transformation step, not a separate pipeline run. ADF Mapping Data Flow can project, filter, and mask in one pass.
3
Use incremental / watermark-based loads, not full dumps. For a 50GB Oracle table, never do a full extract every night. Use a high-watermark column (e.g., last_updated_ts) and only move records changed since the last run. Reduces network traffic, load on source, and pipeline runtime drastically.
4
Match compression to the use case. Landing zone → use gzip (compact, write-once). Bronze/Silver → use snappy (fast decompression for reads). Transferring between cloud regions → compress before transfer to reduce egress cost.
5
Isolate integration runtime to source proximity. Self-Hosted Integration Runtime (SHIR) should sit as close to the on-prem source as possible — ideally same subnet — to minimize latency. In Kahramaa, SHIR was deployed in the Qatar utility data center co-located with Oracle ERP.
6
Idempotency — every pipeline run should be safe to re-run. Write to temp partition first, validate, then atomic rename/overwrite. Delta Lake's ACID transactions give you this by default. In ADF, use staging blobs + Databricks MERGE to ensure no duplicates even on retry.
100MB / 256MB file-size rule: When writing to ADLS or Delta, aim for 128–256MB files. Too many small files (small file problem) hammers the metadata store and slows Spark reads significantly. In ADF Data Flow, use the "Optimize" tab → "Set partitioning" to control output file count. In Databricks, use OPTIMIZE and VACUUM regularly on Delta tables.
Q07
Data Fragmentation
Architecture / DB

Data fragmentation refers to dividing a large dataset across multiple physical locations, nodes, or files — either deliberately (to improve performance and parallelism) or unintentionally (causing inefficiency).

Two types of intentional fragmentation (distributed DB context):

TypeDescriptionExample
Horizontal Fragmentation
(Sharding)		 Rows are split across nodes. Each node holds a subset of rows based on a partition key. Meter readings split by emirate/region — Abu Dhabi data on Node 1, Dubai data on Node 2
Vertical Fragmentation Columns are split across nodes. Each node holds specific columns of the same rows. Customer table: PII columns (name, DOB) on secure node; usage columns on analytics node
Mixed Fragmentation Combination of both Region-based row sharding + separate column stores per team
Negative fragmentation — the Small Files Problem in Delta Lake: In our IoT streaming pipeline (2.8M events/day), early runs wrote one file per micro-batch — resulting in 5000+ files per day in the Bronze table. Spark had to open and read metadata for every file, causing query times of 4+ minutes for a simple aggregate. Fixed by: (1) increasing trigger interval in Structured Streaming from 30s to 5 min, (2) running OPTIMIZE daily via Databricks Jobs to compact small files into 128MB chunks, and (3) VACUUM weekly to remove stale files. Query time dropped to ~18 seconds.
# Fix Delta Lake file fragmentation # Compact small files (OPTIMIZE) spark.sql("OPTIMIZE bronze.iot_meter_readings ZORDER BY (zone_id, read_date)") # Remove old file versions (VACUUM — keep 7 days) spark.sql("VACUUM bronze.iot_meter_readings RETAIN 168 HOURS")

Fragmentation in relational DBs: Index fragmentation occurs when INSERT/DELETE operations cause B-tree index pages to become out-of-order or sparsely filled. In SQL Server, ALTER INDEX REBUILD defragments the index. In Oracle, ALTER TABLE ... MOVE reclaims space. This was relevant in our Oracle ERP source — heavy daily INSERTs caused index fragmentation, and scheduled rebuilds were part of the source DB DBA's routine.

Q08
How Did You Design ADF — Step by Step Process?
ADF Design

Here's how I designed the ADF architecture for Kahramaa's data platform — ground up, step by step:

1
Source Analysis & Connectivity Planning
Catalogued all 4 source systems. Oracle ERP was on-prem → needed Self-Hosted Integration Runtime deployed in Qatar DC. MySQL CRM was cloud-hosted → used Azure IR. SharePoint → REST connector. Event Hubs → Databricks Auto Loader (ADF not used for streaming). Documented connection strings, credentials, and service accounts. Stored all secrets in Azure Key Vault with Key Vault Linked Service references — no credentials in ADF JSON.
2
Linked Services & Dataset Templates
Created parameterised Linked Services (e.g., one Oracle LS with @{linkedService().host} as a parameter). Created Dataset templates where table name and schema were runtime parameters. This meant one Dataset definition could serve all 15+ Oracle tables.
3
Metadata-Driven Control Table
Built a SQL control table: pipeline_config with columns: source_system, table_name, load_type (full/incremental), watermark_column, last_run_watermark, target_path, is_active. The master pipeline did a Lookup Activity on this table, then passed each row to a ForEach Activity.
4
Pipeline Hierarchy: Master → Child
Master pipeline: Lookup → ForEach → Execute Pipeline (child). Child pipeline: accepted parameters, ran Get Watermark → Copy Activity (source to Bronze ADLS) → Update Watermark → Trigger Databricks notebook. Used If Condition Activity inside child to branch on full vs. incremental load type.
5
Error Handling & Retry Logic
Each Copy Activity had 3 retries with 30-second intervals. Pipeline-level failure path triggered an Azure Logic Apps alert (email + Teams notification with pipeline name, error message, run ID). Partial failures were logged to a pipeline_error_log table. The next run picked up from last successful watermark — no data loss.
6
Scheduling & Triggering
Batch pipelines: Schedule trigger at 01:00 AM GST. Event-based trigger on ADLS for file arrival (SharePoint exports dropped files → trigger fired automatically). Tumbling window trigger for hourly micro-batch aggregations on meter data.
7
CI/CD via Azure DevOps
ADF connected to Git (Azure DevOps repo). All pipeline JSON configs versioned. Used ARM template export for deployment from Dev → UAT → Prod. Parameter files per environment. No manual changes in Prod — all changes through PRs.
Result: 32 pipelines managing ~25–30 GB/day batch ingestion from 4 source systems, all driven by a single control table. Adding a new table required inserting one row into the config table — zero code changes.

Q10
How Do You Monitor Data?
Monitoring / Ops

Monitoring has three layers in our Kahramaa platform: Pipeline Monitoring, Data Quality Monitoring, and Infrastructure Monitoring.

1. Pipeline Monitoring (ADF + Databricks):

  • ADF Monitor Hub: Real-time view of all pipeline runs. Filter by status (Failed, InProgress), activity name, and trigger type. For each failed run: click into Activity runs → see exact error message, retry count, and duration per activity.
  • Azure Monitor + Log Analytics: Configured Diagnostic Settings on ADF to push pipeline logs to Log Analytics workspace. KQL queries to alert on pipeline failures: ADFPipelineRun | where Status == "Failed". Set alert rules with Action Groups sending Teams + email notifications within 5 minutes of failure.
  • Databricks Job Alerts: Job run email notifications configured for Failure and Success. For long-running jobs, Ganglia metrics within Databricks showed CPU/memory per executor in real time.

2. Data Quality Monitoring (Great Expectations):

  • Expectation suites defined for each Silver/Gold table: not-null checks on key columns, value range checks (consumption_kwh > 0 and < 50000), row count threshold checks (±20% from 30-day rolling average — flags partial loads).
  • Checkpoints ran as the final step of each Databricks notebook. If any expectation failed, the notebook raised an exception — halting the pipeline before bad data reached Gold/Power BI.
  • Data Docs (GE's HTML report) published to ADLS and accessible via Databricks Jobs. Operations team could see which tables passed/failed QC without accessing Databricks directly.

3. Data Lineage & Governance (Azure Purview):

  • Azure Purview scanned ADLS, ADF, and Databricks automatically to build lineage graphs. Could trace a Gold table column back to its Bronze source file and original Oracle table column.
  • Useful for impact analysis: "If we change this Oracle column, which 3 Power BI reports are affected?" — answered in Purview in seconds.
SLA monitoring example: Gold layer tables had a business SLA of 07:00 AM availability. Configured Azure Monitor alert: if ADF pipeline "gold_layer_refresh" didn't show "Succeeded" status by 06:45 AM, alert fired. Operations team had 15 minutes to investigate before business users arrived. This proactive monitoring reduced data-related support tickets by ~60% in the first quarter.

Kafka Experience
Streaming / Kafka
Honest position: In Kahramaa, we used Azure Event Hubs for IoT streaming — which is Kafka-protocol compatible. I'll lead with that connection, then cover Kafka concepts I know deeply.

Kafka-compatible experience via Azure Event Hubs:

Azure Event Hubs exposes a Kafka endpoint — meaning any Kafka producer/consumer SDK connects to it unchanged. In Kahramaa, 300K+ smart meters (electricity and water) published telemetry events — ~2.8 million events per day — to Event Hubs topics (equivalent to Kafka topics). Our Databricks Structured Streaming consumed these using the Kafka connector (spark.readStream.format("kafka")), pointing at the Event Hubs Kafka endpoint. This gave me hands-on experience with offset management, consumer groups, and exactly-once semantics — the same concepts as native Kafka.

# Reading from Event Hubs via Kafka protocol in Databricks df_stream = (spark.readStream .format("kafka") .option("kafka.bootstrap.servers", "kahramaa-eh.servicebus.windows.net:9093") .option("subscribe", "iot-meter-readings") .option("startingOffsets", "latest") .option("kafka.security.protocol", "SASL_SSL") .load() ) # Parse JSON payload from Kafka value (binary → string → JSON) df_parsed = df_stream.selectExpr("CAST(value AS STRING) as json_payload", "timestamp") \ .select(F.from_json(F.col("json_payload"), meter_schema).alias("data"), "timestamp") \ .select("data.*", "timestamp")

Kafka concepts I work with:

ConceptWhat It DoesHow We Used It
Topics & Partitions Topic = named stream. Partitions = parallel lanes. More partitions = higher throughput. Event Hubs with 32 partitions matching our 32-executor Databricks cluster for 1:1 parallelism
Consumer Groups Independent readers of same topic. Each group tracks its own offset. One group for real-time anomaly detection, separate group for Bronze ingestion — both read the same Event Hub independently
Offsets Bookmark per partition. Controls where consumer resumes after restart. Databricks checkpoints stored offset → guaranteed no data loss or duplication on restart
Retention How long messages stay in Kafka (default 7 days). Replay possible within retention window. Event Hubs set to 3-day retention — allowed replaying missed events if Bronze pipeline had downtime
Watermarking In Spark Streaming: tells Spark how late data can arrive before state is dropped. withWatermark("event_time", "10 minutes") — allowed 10-min late IoT events before window closed
If asked about native Kafka (without Event Hubs): The architecture is identical — brokers instead of Event Hubs namespaces, Zookeeper (or KRaft in newer versions) for broker coordination, and the same producer/consumer API. The Databricks Spark Kafka connector works with both. My gap is production Kafka broker administration (topic creation, replication factor tuning, ISR management) — for which I'd rely on the platform/ops team, just as in Kahramaa I relied on Azure managing the Event Hubs broker layer.
