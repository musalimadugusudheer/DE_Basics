"Walk me through a data architecture you designed for a large, complex system."
Weak answer (engineer framing)
"At Kahramaa I built ADF pipelines to pull from Oracle and IoT devices into ADLS. Then I used Databricks to transform the data and loaded it into Power BI dashboards."
Strong answer (architect framing)
"At Kahramaa — a utility managing electricity and water for Qatar — I was responsible for the end-to-end data architecture for their digital transformation programme.

The core challenge was ingesting from heterogeneous sources: Oracle ERP, MySQL, IoT sensors, and REST APIs — each with different latency, volume, and reliability profiles. So I defined a zone-based Lakehouse architecture on ADLS Gen2 with three layers: Bronze for raw immutable ingestion; Silver for cleansed, conformed data with schema enforcement and SCD2 dimensions; and Gold as the consumption layer optimised for BI and self-service analytics.

For the ingestion strategy, I separated batch and streaming workloads — ADF for scheduled batch, Databricks Structured Streaming for near-real-time IoT telemetry — preventing streaming latency from being blocked by heavy batch loads.

For reliability, I implemented Delta Lake with ACID transactions and time travel so any data quality issue could be rolled back to a clean checkpoint without full reprocessing. Query performance on Gold was optimised through partitioning by date and Z-order clustering, reducing retrieval time by over 60%.

The architecture served both operational reporting and self-service analytics via Power BI, with governance enforced through RBAC and PII classification across all zones."
Why this works: Business context → architectural decision → rationale → technical choices → outcome. That is the full architect arc.
"How do you approach data quality at scale?"
Weak answer
"I used Great Expectations in Databricks to run quality checks on the data."
Strong answer
"I treat data quality as a layered strategy, not a single tool.

At the ingestion layer I enforce schema validation and null checks at Bronze — reject or quarantine malformed records early before they propagate downstream. In Empower Retirement I used Databricks Auto Loader with schema inference and drift detection so unexpected fields were flagged rather than silently dropped.

At the transformation layer in Silver, I implemented Great Expectations within Databricks workflows — defining expectations around completeness, referential integrity, and value ranges. Failed expectations halted the pipeline rather than loading bad data into Gold.

At the consumption layer, I use data profiling — row counts, null rates, distribution checks — compared across pipeline runs to catch silent degradation before any dashboard consumer sees it.

Governance-wise, Unity Catalog lineage tracking means when a quality issue is found, we can trace exactly which source record caused it and which downstream reports are affected."
Covers the full lifecycle: prevention → validation → monitoring → traceability. That is quality architecture, not just a tool mention.
"How do you define a workload migration strategy from on-prem to cloud?"
Weak answer
"I migrated Oracle databases to Azure using Databricks and ADF."
Strong answer
"I follow a phased approach: assess, design, execute, validate.

Assess: Catalogue existing workloads — volumes, query patterns, SLAs, dependencies, data sensitivity. At Kahramaa we mapped every Oracle schema, classified tables as hot/warm/cold, and identified PII data requiring masking during migration.

Design: Choose the migration pattern. For Kahramaa we used lift-and-extend — not just lifting to Azure, but redesigning into a Lakehouse architecture, replacing Oracle views with Delta tables and Spark transformations.

Execute: Migrate in waves — non-critical historical data first, then operational tables in parallel-run mode where both Oracle and Azure were live simultaneously. ADF Integration Runtime maintained secure hybrid connectivity during the transition.

Validate: Row counts, checksums, and business KPI comparisons before every cutover. No wave signed off without reconciliation reports approved by the business.

Risk management throughout — every wave had a rollback plan, and Oracle source remained read-only for 30 days post-cutover as a safety net."
Structured thinking + risk awareness + business alignment = architect-level answer.
"How do you approach data security and governance in a large architecture?"
Weak answer
"I implemented RBAC and PII compliance using Unity Catalog and Azure Key Vault."
Strong answer
"I treat security as a four-pillar framework: access control, data classification, encryption, and auditability.

Access control: RBAC at platform level via Unity Catalog — fine-grained privileges at catalog, schema, and table level. Engineers write to Bronze/Silver, analysts read Gold, business users access curated views only. At Kyndryl for NAB I also enforced Azure Private Endpoints so all data traffic stayed within the private network — no public internet exposure.

Data classification: Automated PII detection and tagging — national IDs, phone numbers, account numbers are tagged in Unity Catalog and those tags drive dynamic masking policies automatically for non-privileged roles.

Encryption: At rest via ADLS Gen2 built-in encryption, in transit via TLS. All secrets — API keys, connection strings — stored in Azure Key Vault, never hardcoded.

Auditability: Unity Catalog audit logs combined with Azure Monitor give a complete trail — who accessed what data, when, and from where. This was critical for NAB where regulatory compliance required demonstrable access controls."
Four-pillar structure is memorable and comprehensive. Interviewers can follow each dimension clearly.
The PACE framework — structure every architecture answer
P Problem — what was the business challenge?
Start with business context, not technology. "Kahramaa needed to move from manual reporting to self-service analytics across electricity and water operations." This anchors everything that follows in real impact.
A Architecture decision — what did you design and why?
Describe structure and reasoning. why Delta Lake not just used Delta Lake. why separate batch and streaming not just built streaming. The "why" is what separates architects from engineers.
C Challenges — what risks or constraints did you navigate?
Mention at least one: data quality issues, legacy constraints, compliance, performance, skill gaps. Architects are known for managing complexity, not pretending it doesn't exist.
E Evidence — what was the measurable outcome?
Quantify where possible: 40% automation, 60% query improvement, 95% success rate. If no metric, describe business impact: "enabled self-service analytics for business teams for the first time."
Apply PACE to every architecture question. Takes 30 seconds to mentally structure before speaking — and makes you sound like someone who operates at a senior level routinely.
