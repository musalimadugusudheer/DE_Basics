Scenario 1 — Heterogeneous multi-source ingestion architecture

The Problem
Kahramaa operated with data scattered across Oracle ERP (structured, batch), MySQL operational databases (structured, near-real-time), IoT sensor devices across the electricity and water grid (semi-structured JSON, high-frequency streaming), and REST APIs from third-party systems. Each had completely different latency profiles, formats, reliability characteristics, and ownership. There was no unified data platform — each system was siloed, engineers ran manual exports, and business teams waited days for reports. There was no single source of truth for any operational metric.
Architectural Decision
Designed a unified Lakehouse on ADLS Gen2 with a strict zone separation strategy. The key architectural decision was to separate ingestion patterns by source latency profile rather than building one generic pipeline for everything. Oracle ERP → ADF batch (daily/hourly schedule). MySQL → ADF with change watermark (15-min incremental). IoT sensors → Event Hubs + Structured Streaming (sub-minute latency). REST APIs → ADF HTTP connector with pagination (scheduled + event-triggered). Each path lands into the same Bronze zone but through optimised connectors. This avoids the anti-pattern of forcing low-latency IoT data through a batch pipeline, or wasting streaming resources on slowly changing ERP data.
Technique: High-watermark incremental ingestion for MySQL
Instead of full table dump on every run, track the last processed timestamp in a control table. Each run extracts only records where updated_at > last_watermark. Atomic watermark update only after successful load — guarantees no data loss if pipeline fails mid-run.
PySpark — High-watermark incremental ingestion with control table (Kahramaa MySQL pattern)

How to say this in the interview
"The first architectural challenge at Kahramaa was that we had four completely different source systems with incompatible latency profiles. The mistake most teams make is building one generic pipeline for everything — typically a daily batch job. That would mean IoT sensor data, which needed sub-minute freshness for operational dashboards, sitting in an overnight queue next to ERP data that only updates weekly.

My architectural decision was to separate ingestion patterns by source latency, not by source type. I classified sources into three tiers: real-time (IoT → Event Hubs streaming), near-real-time (MySQL → incremental JDBC with high-watermark), and batch (Oracle ERP → ADF scheduled). Each tier had its own ingestion cluster, its own SLA, and its own alerting threshold. All paths converged in the same Bronze zone on ADLS Gen2 — so downstream Silver processing was unified regardless of how the data arrived.

The watermark pattern I implemented for MySQL was critical for reliability — the watermark was only advanced after a confirmed successful write to Delta Lake. If the pipeline failed mid-run, the next run would re-extract from the last confirmed watermark. No data loss, no duplication."

Scenario 2 — IoT real-time streaming with late-arriving device data

The Problem
Kahramaa's electricity grid and water network had thousands of IoT sensors reporting readings every 30 seconds. Many sensors operated in remote areas with intermittent connectivity — a sensor could go offline for hours and then flood the pipeline with buffered readings when it reconnected. The original approach was to ingest these via hourly ADF batch jobs, which meant: (1) a sensor that went offline at 10:00 and reconnected at 14:00 would send 4 hours of readings at 14:00, all of which would be stamped with ingestion time 14:00 — completely destroying the time-series accuracy of the operational dashboard. (2) Any anomaly detection based on reading timestamp would fail because the timestamps were wrong.
Architectural Decision — Event-time streaming with two-path late arrival handling
Replaced ADF batch with Event Hubs + Databricks Structured Streaming. Key decision: process on event_time (the timestamp the sensor took the reading) not processing_time (when it arrived at the pipeline). Implemented a 90-minute watermark based on measurement of P99 offline duration across the sensor fleet. Events arriving within 90 minutes of event_time are included in the correct window automatically. Events arriving later than 90 minutes route to a late-arrival staging table, corrected in a nightly MERGE job using Delta time travel for audit.
PySpark Structured Streaming — IoT event-time processing with watermark + late arrival routing
from pyspark.sql import functions as F from pyspark.sql.types import StructType, StructField, StringType, DoubleType, TimestampType # IoT payload schema — always define explicitly, never infer in streaming iot_schema = StructType([ StructField("sensor_id", StringType(), False), StructField("asset_id", StringType(), False), StructField("reading_value", DoubleType(), True), StructField("unit", StringType(), True), StructField("event_time", TimestampType(), False), # sensor reading timestamp StructField("battery_level", DoubleType(), True), StructField("transmission_type", StringType(), True) # "live" or "buffered" ]) # Read from Event Hubs raw_stream = ( spark.readStream.format("eventhubs") .options(**{ "eventhubs.connectionString": dbutils.secrets.get("kahramaa-kv", "eventhub-conn"), "eventhubs.consumerGroup": "iot-silver-consumer", "eventhubs.maxEventsPerTrigger": "50000" # backpressure control }) .load() .select(F.from_json(F.col("body").cast("string"), iot_schema).alias("data"), "enqueuedTime") .select("data.*", "enqueuedTime") ) # Classify late arrivals BEFORE watermark logic classified_stream = raw_stream.withColumn( "arrival_lag_minutes", (F.unix_timestamp("enqueuedTime") - F.unix_timestamp("event_time")) / 60 ).withColumn( "arrival_class", F.when(F.col("arrival_lag_minutes") > 90, "LATE") .when(F.col("arrival_lag_minutes") < 0, "FUTURE") # clock skew .otherwise("ON_TIME") ) # PATH 1: On-time events — windowed aggregation on event_time ontime_stream = classified_stream.filter(F.col("arrival_class") == "ON_TIME") windowed_readings = ( ontime_stream .withWatermark("event_time", "90 minutes") .groupBy( F.window("event_time", "5 minutes"), "sensor_id", "asset_id" ) .agg( F.avg("reading_value").alias("avg_reading"), F.min("reading_value").alias("min_reading"), F.max("reading_value").alias("max_reading"), F.count("*").alias("reading_count"), F.first("unit").alias("unit") ) .withColumn("window_start", F.col("window.start")) .withColumn("window_end", F.col("window.end")) .drop("window") ) # Write windowed aggregates to Silver — append mode for time-series q1 = ( windowed_readings.writeStream .format("delta") .outputMode("append") .option("checkpointLocation", "/mnt/checkpoints/iot_windowed") .partitionBy("window_start") .trigger(processingTime="30 seconds") .start("/mnt/silver/iot_readings_windowed") ) # PATH 2: Late events — route to staging for nightly correction late_stream = classified_stream.filter(F.col("arrival_class") == "LATE") q2 = ( late_stream.writeStream .format("delta") .outputMode("append") .option("checkpointLocation", "/mnt/checkpoints/iot_late_staging") .trigger(processingTime="30 seconds") .start("/mnt/silver/iot_late_arrival_staging") ) spark.streams.awaitAnyTermination()
PySpark — Nightly late arrival correction job (Delta MERGE + time travel audit)
# Nightly job: merge late IoT events into historical windowed aggregates from delta.tables import DeltaTable import datetime yesterday = (datetime.date.today() - datetime.timedelta(days=1)).isoformat() # Load late events that belong to yesterday's windows late_events = spark.read.format("delta").load("/mnt/silver/iot_late_arrival_staging") \ .filter(F.to_date(F.col("event_time")) == yesterday) # Re-aggregate the late events into 5-min windows late_agg = ( late_events .groupBy( F.window("event_time", "5 minutes"), "sensor_id", "asset_id" ) .agg( F.avg("reading_value").alias("late_avg"), F.count("*").alias("late_count") ) .withColumn("window_start", F.col("window.start")) .drop("window") ) # MERGE into Silver — update existing windows to include late data silver_table = DeltaTable.forPath(spark, "/mnt/silver/iot_readings_windowed") silver_table.alias("target").merge( late_agg.alias("source"), """target.sensor_id = source.sensor_id AND target.asset_id = source.asset_id AND target.window_start = source.window_start""" ).whenMatchedUpdate(set={ # Weighted average combining original and late readings "avg_reading": """( (target.avg_reading * target.reading_count) + (source.late_avg * source.late_count) ) / (target.reading_count + source.late_count)""", "reading_count": "target.reading_count + source.late_count", "_late_corrected": "true", "_correction_ts": "current_timestamp()" }).whenNotMatchedInsert(values={ # Window existed only in late data — insert fresh "sensor_id": "source.sensor_id", "asset_id": "source.asset_id", "window_start": "source.window_start", "avg_reading": "source.late_avg", "reading_count": "source.late_count", "_late_corrected": "true" }).execute() print(f"Late arrival correction complete for {yesterday}") # Delta time travel preserves pre-correction state: # SELECT * FROM delta.`/mnt/silver/iot_readings_windowed` TIMESTAMP AS OF '2025-03-25 01:59:00'
Interview answer
"A key architectural challenge at Kahramaa was IoT sensors in remote areas of the grid going offline and reconnecting with batches of buffered readings. The original ADF batch approach stamped everything with ingestion time — destroying time-series accuracy.

My solution was a two-path event-time streaming architecture. I moved to Event Hubs + Databricks Structured Streaming, processing on sensor event_time not pipeline processing_time. I measured the P99 offline duration across the sensor fleet — it was 72 minutes — and set a 90-minute watermark as the primary path. 99% of late events were handled automatically by the watermark.

For the remaining 1% arriving after 90 minutes — usually sensors in truly remote locations — I classified them at ingestion and routed to a late-arrival staging table. A nightly correction job ran a weighted-average MERGE back into the historical windowed aggregates using Delta Lake. Critically, Delta time travel preserved the pre-correction state — so if the correction itself had an error, we could roll back and the audit trail was intact."

Scenario 3 — Oracle to Azure migration with zero downtime

The Problem
Kahramaa's core operational data lived in Oracle databases running on-premise. The migration to Azure had to be done with zero downtime — operations could not stop for a maintenance window. Additionally, the Oracle schemas were legacy with poor documentation, had circular foreign key dependencies, and some tables had 10+ years of data (hundreds of millions of rows). A naive lift-and-shift would replicate the same poor data model into Azure — missing the opportunity to redesign for modern analytics.
Architectural Decision — Lift-and-extend with parallel run validation
Three-phase migration: (1) Shadow phase — ADF Integration Runtime replicates Oracle to Bronze in Azure while Oracle remains the system of record; (2) Parallel run — both Oracle and Azure Gold layer are live, business users validate Azure numbers match Oracle; (3) Cutover — Oracle set to read-only, Azure becomes system of record. Key design: Oracle schemas were NOT replicated as-is into Azure. Bronze preserved the raw Oracle structure (lift), Silver cleaned and conformed it, Gold redesigned into a star schema (extend). This separated the migration risk from the redesign risk.

Interview answer
"The Oracle migration at Kahramaa had two constraints that ruled out a simple lift-and-shift: zero downtime requirement, and the Oracle schema was 10+ years of accumulated technical debt that we didn't want to replicate into Azure.

I designed a lift-and-extend migration with three phases. In the shadow phase, ADF Integration Runtime ran alongside Oracle — replicating every change to Bronze in Azure while Oracle remained the system of record. In the parallel run phase, both systems were live and business users validated that Azure Gold layer numbers matched Oracle exactly. Once parity was confirmed over a 2-week validation window, we cut over — Oracle went read-only, Azure became the source of truth.

The 'extend' part was the Silver transformation — rather than preserving Oracle's messy column names, date formats, and circular dependencies, I redesigned the data model into clean dimension and fact tables with SCD2 tracking. The MERGE was hash-based — I computed an MD5 of the business-critical columns, and only triggered an SCD2 new-row insertion when the hash changed. This meant Oracle records that hadn't changed in years didn't generate unnecessary new rows in the dimension table."

Scenario 4 — Data governance, RBAC & PII compliance framework

The Problem
Kahramaa's data included customer personal information — names, national IDs, addresses, consumption data — all regulated under Qatar's data protection regulations. The original setup had no access controls — any engineer with ADLS access could read any data. There was no data classification, no audit trail of who accessed what, and no lineage showing where customer PII flowed. A compliance audit was approaching and the organisation had no defensible position.
Architectural Decision — Four-pillar governance framework
Implemented a governance framework across four dimensions simultaneously: (1) Classification — automated PII tag detection and column-level tagging in Unity Catalog; (2) Access control — Unity Catalog RBAC with four personas (data_engineer, data_analyst, business_user, compliance_officer), each with different privilege levels per zone; (3) Dynamic masking — sensitive columns auto-masked for non-privileged roles — analysts see masked national_id, compliance officers see full values; (4) Lineage + audit — Unity Catalog system tables + Azure Monitor for complete data access audit trail.

Scenario 5 — Gold layer query performance optimisation

The Problem
After migrating data to Azure and building the Gold layer, Power BI dashboard queries against the Gold consumption tables were timing out. A simple "total consumption by region for the last 30 days" query was scanning 3 years of data and taking 4–6 minutes. Business users found the dashboards unusable. Root cause: no partitioning strategy, no Z-order clustering, and the Gold layer had accumulated thousands of small files from incremental Databricks writes.
Architectural Decision — Three-layer optimisation strategy
Applied optimisations in three layers: (1) Partition pruning — partition Gold fact table by consumption_date so date-filtered queries skip 99% of data; (2) Z-order clustering — co-locate rows with the same region_code and asset_type on the same files so region/type filters need fewer file reads; (3) Compaction — OPTIMIZE to merge thousands of small files into fewer large files, reducing file-open overhead. Scheduled OPTIMIZE on cold partitions (>1 day old) at 2 AM — never on active streaming partitions.

Scenario 1 — Graph-based network topology model in Delta Lake

The Problem
NAB's hybrid network (on-premise + AWS Public Cloud Connect) had thousands of devices — routers, switches, firewalls, load balancers — with complex dependency relationships. A change to one device could cascade and break ten others. The traditional approach was manual dependency mapping in spreadsheets — incomplete, always out-of-date, and unable to detect circular dependencies. This made automated change eligibility assessment impossible — you couldn't safely automate a change without knowing its blast radius.
Architectural Decision — Graph topology as Delta Lake edge/node tables
Modelled the network as a graph: devices as nodes (with SCD2 versioned configuration state), connections as edges (with directionality and dependency type). Stored as two Delta tables: dim_network_node (device configuration history) and fact_network_edge (connection relationships with effective dates). PySpark graph traversal algorithms computed blast radius and dependency chains on demand. This enabled the automation engine to evaluate: "if I change device X, which downstream devices are affected, and do any of those have active SLAs?"

Scenario 3 — Change window scheduling optimisation with OR-Tools

The Problem
NAB's weekend change window had hard constraints: maximum 200 changes per 4-hour window, changes must be sequenced to avoid dependency conflicts, high-risk changes require human approval slots, and certain device types cannot be changed simultaneously. Manual scheduling by network engineers took hours and still produced suboptimal results — often leaving 30–40% of the window capacity unused.
Architectural Decision — Integer Linear Programming solver on PySpark
Used Google OR-Tools (Integer Linear Programming) to optimise change scheduling as a constraint satisfaction problem. Variables: binary assignment of each eligible change to each available time slot. Objective: maximise total changes scheduled. Constraints: dependency ordering, risk tier limits per slot, device type concurrency limits, SLA protection. PySpark computed the input data (eligible changes, graph-based dependencies, risk scores) from the Silver layer and fed it to OR-Tools. The solver ran in minutes and produced a schedule that consistently utilised 90%+ of the window.
PySpark + OR-Tools — Change window scheduling optimiser
from ortools.sat.python import cp_model from pyspark.sql import functions as F # ── Step 1: Load eligible changes from Silver ───────────────────────────────── eligible_changes = ( spark.read.format("delta").load("/mnt/silver/change_requests") .filter( (F.col("auto_eligible") == True) & (F.col("change_status") == "APPROVED") & (F.col("processed") == False) ) .select("change_request_id", "target_device_id", "risk_score", "estimated_duration_min", "device_type") .collect() ) changes = [row.asDict() for row in eligible_changes] num_changes = len(changes) num_slots = 20 # 20 × 12-min slots = 4-hour window MAX_PER_SLOT = 10 MAX_HIGH_RISK_SLOT = 2 # ── Step 2: Build OR-Tools CP-SAT model ────────────────────────────────────── model = cp_model.CpModel() # Binary variable: assigned[i][j] = 1 if change i scheduled in slot j assigned = {} for i in range(num_changes): for j in range(num_slots): assigned[(i, j)] = model.NewBoolVar(f"change_{i}_slot_{j}") # Constraint 1: Each change scheduled in at most one slot for i in range(num_changes): model.AddAtMostOne(assigned[(i, j)] for j in range(num_slots)) # Constraint 2: Max 10 changes per slot for j in range(num_slots): model.Add(sum(assigned[(i, j)] for i in range(num_changes)) <= MAX_PER_SLOT) # Constraint 3: Max 2 high-risk changes per slot for j in range(num_slots): high_risk_in_slot = [ assigned[(i, j)] for i, c in enumerate(changes) if c["risk_score"] > 0.7 ] if high_risk_in_slot: model.Add(sum(high_risk_in_slot) <= MAX_HIGH_RISK_SLOT) # Objective: maximise total changes scheduled (weighted by risk inverse) model.Maximize( sum( assigned[(i, j)] * int((1 - changes[i]["risk_score"]) * 100) for i in range(num_changes) for j in range(num_slots) ) ) # ── Step 3: Solve and write schedule to Gold ───────────────────────────────── solver = cp_model.CpSolver() status = solver.Solve(model) schedule = [] if status in (cp_model.OPTIMAL, cp_model.FEASIBLE): for i in range(num_changes): for j in range(num_slots): if solver.Value(assigned[(i, j)]): schedule.append({ "change_request_id": changes[i]["change_request_id"], "assigned_slot": j, "slot_start_time": f"Saturday 22:00 + {j*12} min" }) schedule_df = spark.createDataFrame(schedule) schedule_df.write.format("delta").mode("overwrite") \ .save("/mnt/gold/change_schedule_weekend") print(f"Scheduled {len(schedule)} / {num_changes} eligible changes") # Typical result: 180+ of 200 eligible → 90%+ utilisation vs 60% manual
