Monthly data volume handled is approximately 500 TB.
Kahramaa Kyndryl/NAB
▼ expand

Again, I want to give you an honest picture. My Kahramaa platform currently processes around 537 GB of raw data per month through the pipelines — that's 50 million IoT readings daily plus Oracle and CRM batch feeds. At full deployment of 2 million meters in 2027, that scales to approximately 1.1 TB per month in raw ingestion, with multi-layer copies pushing total monthly pipeline throughput higher.

At the architecture level, handling 500 TB monthly is about two things: throughput management and cost-efficient storage. For throughput, the key design decisions I would apply from my experience are — parallel JDBC extraction with at least 80 partitions on any relational source, Event Hub partitioning aligned to the number of stream consumers, Databricks Structured Streaming with a 10-second trigger interval for near-real-time pipelines, and batch jobs sized with enough executor cores so that no single stage exceeds 30 minutes. For storage, 500 TB raw per month compresses to roughly 100–125 TB in Delta format with Snappy compression, which is the number that actually sits in ADLS and drives your storage cost.

The incremental watermark pattern I use at Kahramaa — where each pipeline records its last processed timestamp and only extracts new rows — is what makes 500 TB/month manageable. You never reload what you already have.

Key technical detail At 500 TB/month, or roughly 17 TB/day, the shuffle during a Spark aggregation can itself generate 17+ TB of intermediate data. That's where AQE skew join detection and proper shuffle partition count become critical — without tuning, you'd see spill to disk degrading jobs from minutes to hours.

Q-03
Challenges faced while handling large-scale data computation.
Kahramaa Kyndryl/NAB
▼ expand

A few come to mind that were genuinely hard problems to solve.

The first was the small-file explosion from IoT streaming at Kahramaa. When you have 988,000 meters each sending a reading every 30 minutes, Structured Streaming writes thousands of tiny Parquet files per micro-batch to the Bronze Delta table. Left unchecked, the Bronze table would accumulate 20,000+ files per day, and Delta file listing overhead would make even simple queries crawl. I solved this by implementing a weekly OPTIMIZE pipeline that compacts files to the 128–512 MB target range, combined with Z-ORDER BY (meter_id, event_time) on the most frequent query predicates. That reduced a full-day Bronze scan from over 4 minutes to under 30 seconds.

The second was data skew in aggregations. At Kahramaa, certain distribution zones have significantly higher meter density than others — one municipal zone could account for 30% of all readings. When I first ran daily consumption aggregations grouped by zone_id, that one partition was 10x larger than the others, causing straggler tasks that held up the entire job. I addressed this by enabling AQE with spark.sql.adaptive.skewJoin.enabled=true and tuning the skew factor threshold. For the worst-offending zone I also used a salting technique in a pre-aggregation step.

At Kyndryl/NAB, the challenge was schema evolution on network device data. Different Cisco device generations returned different JSON structures for the same logical field. I implemented Delta Lake's mergeSchema=true option on all Bronze writes and built a Silver normalization layer that mapped all device-specific schemas to a canonical model before any downstream processing touched the data.

Q-04
Details of failures encountered in production environments.
Kahramaa Kyndryl/NAB Empower
▼ expand

I'll share three real production incidents and what I learned from each.

Incident 1 — Checkpoint corruption at Kahramaa. One morning, our streaming pipeline from Event Hubs to Bronze stopped processing. Databricks showed no active query. The root cause was a corrupt checkpoint directory — a partial write during an executor failure had left the checkpoint in an inconsistent state. The immediate fix was to delete the checkpoint and restart the stream from the last committed Event Hub offset, which Delta's transaction log preserved correctly. The lasting fix was to add a pipeline health monitor in ADF that alerts on zero-throughput for more than 15 minutes, so we catch this immediately rather than discovering it hours later during business hours.

Incident 2 — JDBC connection pool exhaustion at Kahramaa. Our hourly Oracle ERP ingestion pipeline started failing intermittently with connection timeout errors. The issue was that ADF was spinning up 20 parallel JDBC partitions simultaneously, which saturated Oracle's connection pool. I fixed this by staggering pipeline triggers using ADF's tumbling window with a 5-minute offset, and reducing numPartitions from 20 to 12 during peak Oracle business hours, reverting at night. I also added a retry policy with exponential backoff on the ADF linked service.

Incident 3 — Silent data loss at Empower/JPMC. A pipeline migrating legacy financial data completed with a green status but the target row count was 3% lower than the source. The failure was silent — no exception was raised. The cause was a PySpark DataFrame write with mode="overwrite" where a partition filter was applied during the write, silently dropping partitions outside the filter. I fixed the immediate data gap with a targeted backfill and permanently addressed the pattern by adding row-count reconciliation checks using Great Expectations after every write — a check that fails loudly rather than passing silently.

What interviewers want to hear Don't just describe the failure — describe the detection, the immediate fix, and the permanent systemic change. That's what distinguishes a production-grade engineer from someone who just fixes and moves on.
Data Quality & Insights
Q-05
Data quality checks implemented.
Kahramaa Empower
▼ expand

Data quality is something I treat as a first-class concern — not an afterthought. I implement it at every layer boundary in the Medallion architecture.

At the Bronze layer, the first gate is schema enforcement — Delta Lake rejects any record that doesn't conform to the defined schema. No exceptions, no silent truncation. The second check is null validation: for IoT readings, meter_id, timestamp, and reading_value cannot be null. Any record failing this goes to a dead-letter quarantine table with an error code, not to the trash.

At the Bronze → Silver transition, I use a five-dimension validation framework. First, row count reconciliation — Silver record count must be within 0.01% of Bronze after applying deduplication rules. Second, financial or measurement sum reconciliation — total kWh consumed in Silver must match total in Bronze. Third, range validation — consumption values must fall within physically plausible bounds per meter type; a water meter showing 10,000 m³ in one reading is flagged as anomalous. Fourth, duplicate detection using a window function on meter_id and timestamp over a 2-hour dedup window — the Siemens AMI system can retransmit readings on network recovery. Fifth, referential integrity — every meter_id in the fact table must have a matching record in DimMeter.

At Empower/JPMC, I used Great Expectations as the validation framework. I defined expectation suites per table — each suite had 15–25 expectations covering column types, value ranges, uniqueness, and statistical distributions. These ran as a Databricks task that gated the Silver→Gold promotion, so bad data could never reach the reporting layer.

On top of this, I built a data quality dashboard in Power BI that shows daily pass/fail rates per pipeline, quarantine record volumes by error type, and trend lines so the business team can see data health at a glance without digging into logs.

Q-07
Feature computation approaches used.
Kahramaa Kyndryl/NAB
▼ expand

When you say feature computation, I interpret that as derived metrics and analytical attributes computed from raw data — the kind of computed columns that make the Gold layer useful for both reporting and downstream ML.

At Kahramaa, the core feature computations happen in PySpark in Databricks during the Silver → Gold transformation. Key examples:

Rolling averages: For each meter, I compute a 30-day rolling average consumption using a PySpark window function with rangeBetween(-30 days in seconds, 0). This feeds directly into the anomaly detection logic — a reading more than 3 standard deviations above the rolling mean gets flagged.

Peak vs off-peak classification: Each electricity reading gets a computed time_of_use_band attribute — Peak (6–10 PM), Shoulder (6 AM–6 PM), or Off-Peak (10 PM–6 AM) — computed from the reading timestamp. This is critical for Kahramaa's tiered tariff billing.

Customer consumption tier: A computed column that classifies customers into Low / Medium / High / Very High consumption bands based on their trailing 90-day total, recalculated daily. The business uses this for demand response programmes.

At Kyndryl/NAB, features were more about network risk scoring — computing derived attributes like change_risk_score based on device criticality, number of dependent connections, time since last successful change, and historical failure rate. I used Databricks SQL to compute these as calculated columns in the Silver layer, then PySpark window functions for time-series features like rolling change failure rates per device type.

Q-10
Scheduling mechanisms used in pipelines.
Kahramaa Kyndryl/NAB
▼ expand

I use different scheduling mechanisms depending on the nature of the pipeline, and I think choosing the right trigger type is an important engineering decision that's often overlooked.

At Kahramaa, I run three different trigger patterns. For IoT streaming, it's continuous — Structured Streaming runs as a persistent Databricks job with a 10-second processing trigger, continuously consuming from Azure Event Hubs. There's no schedule; the pipeline runs 24/7. For Oracle ERP batch ingestion, I use ADF scheduled triggers with hourly incremental loads — the trigger fires every hour, the pipeline reads the watermark from a metadata Delta table, extracts only rows where LAST_UPDATED > watermark, and writes them to Bronze. For the Silver and Gold transformation jobs, I use ADF tumbling window triggers with a 2-hour window — this ensures exactly-once processing semantics so even if a window fails and retries, data isn't duplicated. The end-of-day Gold aggregation runs on a daily schedule at 2 AM when Oracle activity is lowest.

For maintenance pipelines — OPTIMIZE, VACUUM, Power BI dataset refresh — I use weekly scheduled triggers during weekends when query load is minimal.

At Kyndryl/NAB, I also used event-based triggers: when a new change request file landed in an ADLS container from ServiceNow, an ADF storage event trigger would automatically kick off the ingestion and eligibility assessment pipeline within seconds. No polling, no wasted compute.

CDP / Oozie Context for ENBD In a Cloudera CDP environment, Oozie serves the same orchestration role as ADF. It uses workflow.xml for pipeline definition and coordinator.xml for scheduling — functionally equivalent to ADF's pipeline definition and trigger configuration. My orchestration principles transfer directly; the syntax is different, but the design patterns — dependency management, retry logic, watermarking, event-driven triggers — are identical.
Testing, Code Quality & Operations
Q-11
Testing mechanisms implemented in the project.
Kahramaa Empower SLK
▼ expand

Testing in data engineering is different from application testing — you're not just testing code behaviour, you're testing data transformations, so the test strategy needs to cover both dimensions.

For unit testing, I write pytest test suites for all PySpark transformation logic. Each transformation function gets its own test class with test data created using explicit schemas and typed values — proper Decimal types for financial amounts, proper Date types for timestamps, not string approximations. I mock SparkSession using a local SparkSession.builder.master("local[2]") instance so tests run without a cluster. Test fixtures are reusable across classes so I'm not repeating data setup code.

For integration testing, I test pipeline components end-to-end in a development Databricks environment against a sanitized copy of production data. This validates that the full chain — ingestion, transformation, validation, write — produces the expected row counts and schema at each layer.

For data contract testing, I validate that the schema of each Delta table matches its documented contract before any downstream pipeline reads from it. Schema drift alerts fire to Azure Monitor if a source system adds or changes a column unexpectedly.

At Empower/JPMC, I formalized the test strategy further using Great Expectations as the data assertion layer — each pipeline stage had an expectation suite with 15–25 assertions that ran as part of the pipeline itself, not as a separate QA step.

For regression testing, before any pipeline code change goes to production, I run a row count and sum reconciliation between the new pipeline output and the previous version's output on a shared test dataset. The change can only be promoted if both match within a defined tolerance.

Q-13
Test coverage maintained at 80 percent.
SLK / PSG Kahramaa Empower
▼ expand

80% coverage is the floor, not the target, in my experience. That was the enforced minimum at SLK Software through SonarQube, and it's the standard I've maintained since.

I measure coverage using pytest-cov — specifically with the --cov-report=html flag so I can visually inspect which branches are missed. The command I run before any PR is: pytest --cov=src --cov-fail-under=80. If coverage drops below 80, the test run fails and the build doesn't proceed.

Achieving 80%+ on data engineering code requires covering four categories of tests. Happy path tests: valid input produces correct output — this is the obvious 50–60%. Edge case tests: null inputs, empty DataFrames, zero-value amounts, single-row DataFrames — these add another 15–20% and are where most real-world bugs live. Boundary value tests: for threshold logic like amount >= 10000 triggers HIGH_VALUE, I test exactly 9,999.99, 10,000.00, and 10,000.01. Mocked external dependency tests: JDBC connections and Delta table reads are mocked with unittest.mock.patch so tests run fast and in isolation without needing a live cluster or database.

One thing I'd add: 80% line coverage doesn't automatically mean 80% branch coverage. I always check branch coverage separately — an if/else where only the if is tested shows 100% line coverage but only 50% branch coverage. For financial or data validation logic, I target 80%+ branch coverage specifically.

Q-15
Handling issues across multiple jobs (e.g., issues in 10 jobs out of 100 jobs).
Kahramaa Kyndryl/NAB
▼ expand

This is something I deal with in practice at Kahramaa where we run around 32 ADF pipelines, and at Kyndryl/NAB where we had parallel automation jobs running across dozens of network devices simultaneously. The key principle is: a failure in one job should never cascade into failing healthy jobs, and recovery should be targeted — not a blanket re-run of everything.

Isolation first. I design every pipeline as a fully independent unit with its own watermark, its own checkpoint, and its own success/failure state. An ADF tumbling window trigger ensures each window is independent — if window 7 fails, windows 8 through 12 continue running normally. The failed window will retry automatically up to 3 times with a 10-minute exponential backoff before triggering an alert.

Job status telemetry. I write a job execution record to a Delta metadata table at the end of every pipeline run — job name, run date, status (SUCCESS/FAILED/PARTIAL), rows written, and error message. This gives me a single queryable table across all 32 pipelines. If 10 out of 100 jobs fail, I can run a simple SQL query: SELECT * FROM metadata.job_log WHERE status = 'FAILED' AND run_date = today() and immediately see which 10 failed, what error they threw, and what their last successful run was.

Triage by error type. I categorize failures: transient infrastructure failures (network timeout, connector restart) get automatic retry. Source data failures (null key, unexpected schema) get routed to quarantine with an alert to the data owner — not a pipeline retry, because retrying won't fix a data problem. Logic failures (assertion error, unexpected transformation result) trigger an alert to me directly in Teams via Azure Monitor webhook.

Partial success handling. At Kyndryl/NAB, where we had 40+ network devices being processed in parallel, I tracked which devices completed successfully and which failed. The recovery run would only reprocess the failed devices — never re-process the 90 that already succeeded. I implemented this using a partition-level success flag in the Bronze Delta table, so the Silver job automatically skips partitions that were already promoted successfully.

The discipline that matters The goal isn't zero failures — infrastructure at scale will always have transient failures. The goal is: when failures happen, they're detected in under 15 minutes, isolated from healthy jobs, categorised correctly, and recovered with the minimum reprocessing scope. That's what production-grade looks like.
