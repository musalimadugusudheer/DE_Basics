All dimension tables connect directly to the fact table. Simple joins, fast queries, easy to understand. Best for most analytical use cases.
Dimensions are normalized into sub-dimensions. Saves storage and avoids redundancy, but requires more joins. Better when dimensions are very large or frequently updated.
Use Star schema when...
Query performance is priority
Analysts write SQL directly
Dimensions are small/stable
Simpler BI tooling
Typical OLAP reporting
— Most real-world DWH use this
Use Snowflake schema when...
Dimension tables are very large
Data redundancy is a concern
Frequent dimension updates
Storage cost matters
Complex hierarchies exist
— More joins = slower queries
Interview answer tip: "In my Kahramaa project, the Gold layer was designed as a star schema for Power BI consumption — fact tables for operational metrics and conformed dimension tables for dates, assets, and locations. This gave business users fast, simple query patterns without complex joins."
