Scenario: Customer "Sudheer" moves from Hyderabad to Bengaluru.
Before change
cust_keynamecitysegment
1001SudheerHyderabadPremium
After Type 1 — city is simply overwritten history lost
cust_keynamecitysegment
1001SudheerBengaluruPremium
Pro: Simple, no extra rows, always shows current state.
Con: Historical data is permanently lost — cannot report "sales in Hyderabad last year."
Use when: History doesn't matter. E.g. correcting a typo, updating a phone number, fixing a data entry error.

Pro: Full history preserved. Fact table rows tied to surr_key automatically reflect the correct dimension state at that point in time.
Con: Table grows over time. Queries need is_current=Y filter or date range logic to get current state.
Use when: History matters. This is the most common SCD type in real DWH. Your SCD2 implementation in Kyndryl (PySpark + Databricks) is a perfect example to cite.
Scenario: Customer's segment changes from "Standard" to "Premium".
Before change
cust_keynamesegment
1001SudheerStandard
After Type 3 — a new column added for previous value only 1 version back
cust_keynamecurrent_segmentprev_segment
1001SudheerPremiumStandard
Pro: Single row per entity maintained. Can compare current vs previous in one row without joins.
Con: Only stores one previous version. Third change overwrites prev_segment. Schema changes (new column) needed for each tracked attribute.
Use when: You only need current + one previous value. Rare in practice — Type 2 is usually preferred for historical needs.
