Large-scale data architecture — strategy & roadmap

How a principal architect thinks about designing for a complex organisation — not just a pipeline

The 5-layer architecture thinking model

Every large-scale data architecture decision sits in one of five layers. When you talk about architecture, walk through these layers — it shows you think systemically, not just technically.

Business
What outcomes does data need to enable? Self-service analytics, regulatory reporting, ML models, operational dashboards. This layer drives all decisions below it.
Governance
Who owns data, who can access it, and how is it trusted? Data ownership, stewardship, classification, lineage, quality SLAs, compliance requirements.
Semantic
What does the data mean? Data models, business glossary, conformed dimensions, metric definitions. The layer that makes data consistent across teams.
Processing
How does data move and transform? Ingestion patterns, pipeline orchestration, transformation logic, batch vs streaming, SCD handling, quality checks.
Storage
Where does data live and in what format? Lakehouse zones, table formats (Delta, Iceberg), partitioning, compaction, hot/warm/cold tiering.
Interview answer: "When I approach a large-scale architecture, I start from the business layer — what decisions does this organisation need to make with data? Then I work down: what governance model supports that, what semantic layer makes data consistent across teams, what processing architecture meets the SLAs, and what storage strategy balances cost, performance, and freshness. Every technology choice is a consequence of decisions made in the layers above it."

Building a data strategy & roadmap — the 4-phase model

1
Current state assessment (As-Is)
Inventory all data sources, systems, volumes, formats. Map data flows end-to-end. Identify pain points: data silos, no single source of truth, manual reporting, poor data quality, compliance gaps. At Kahramaa this meant mapping Oracle ERP, MySQL, IoT sensors — each with different owners, update frequencies, and reliability.
2
Target state design (To-Be)
Define the target architecture aligned to business outcomes. Key decisions: centralised vs federated (data mesh), batch vs streaming, single DWH vs Lakehouse vs data fabric, cloud-native vs hybrid. Document architecture decision records (ADRs) — every major choice with alternatives considered and reasoning.
3
Gap analysis & prioritisation
What needs to change to get from As-Is to To-Be? Prioritise by business value vs effort. Typical priority matrix: quick wins (high value, low effort) → strategic (high value, high effort) → fill-ins (low value, low effort) → deprioritise (low value, high effort).
4
Phased roadmap with milestones
Phase 1 (0-3 months): Foundation — core ingestion, governance framework, first Gold layer domain.
Phase 2 (3-9 months): Scale — additional domains, self-service analytics, data quality automation.
Phase 3 (9-18 months): Optimise — real-time capabilities, ML feature store, data products.
Each phase has measurable outcomes — not just technical deliverables but business outcomes.

Architecture patterns for large, complex organisations

Medallion Lakehouse your primary pattern
Bronze (raw) → Silver (conformed) → Gold (domain-optimised). Best for organisations needing both analytical flexibility and governed consumption. You implemented this at Kahramaa and Kyndryl. Key decision: Gold layer can be further split into domain-specific marts.
Data Mesh emerging pattern
Decentralised — each business domain owns its data as a product. Central platform team provides infrastructure. Best for large enterprises with autonomous teams. Requires strong data product contracts and federated governance. Know this exists but don't overclaim experience.
Lambda Architecture legacy but asked about
Separate batch layer (recomputes full history) and speed layer (real-time approximate). Complex to maintain — two codebases for same logic. Largely replaced by Kappa or Delta Lake unified approach. Know it conceptually.
Kappa Architecture modern streaming
Everything is a stream — historical reprocessing done by replaying event log. Simpler than Lambda. Requires a replayable log (Kafka, Event Hubs). Your Kyndryl streaming work is closer to Kappa than Lambda.

Key architectural decisions — what architects get asked

"When would you choose a Lakehouse over a traditional Data Warehouse?"
"Traditional DWH (Synapse, Snowflake, Redshift) is excellent for structured, governed, SQL-based analytics with predictable query patterns. I'd choose it when the organisation has well-defined reporting needs and BI tooling is the primary consumer.

I'd choose a Lakehouse when: (1) the organisation has diverse data types — structured, semi-structured, unstructured — and we need to store raw data before the schema is known; (2) ML workloads need access to the same data as BI; (3) we need to support both streaming and batch on the same storage layer; (4) cost at scale is a concern — ADLS Gen2 storage is far cheaper than DWH compute+storage bundles.

At Kahramaa, the Lakehouse was the right choice because we had IoT sensor data (semi-structured), Oracle relational data, and API JSON — a traditional DWH would have forced us to define schema before we understood the data. The Bronze zone let us land everything raw and figure out the right model in Silver."
"How do you design for scalability in a data platform?"
"Scalability in data platforms has four dimensions: volume, velocity, variety, and concurrency.

Volume: Partition strategy is everything. Partitioning by date is the most common — it enables partition pruning so queries only scan relevant data. Z-order clustering on high-cardinality filter columns (customer_id, product_id) further reduces scan size. At Empower Retirement I reduced query retrieval time by 60% through these techniques alone.

Velocity: Separate ingestion paths for batch and streaming. Don't let heavy batch jobs compete with streaming for cluster resources. Use auto-scaling clusters in Databricks — streaming jobs get dedicated clusters, batch jobs scale to workload.

Variety: Schema-on-read for raw ingestion (Bronze), schema enforcement at Silver using Delta's schema evolution controls. Auto Loader in Databricks handles continuously arriving files without manual intervention.

Concurrency: Separate compute from storage (core Lakehouse principle). Multiple teams can query the Gold layer simultaneously without contention because each spins up its own compute against shared ADLS storage."

Data correctness — ensuring accuracy end-to-end

A principal architect's view of correctness — it's a system property, not a check at one point

The correctness pyramid

Data correctness operates at multiple levels simultaneously. Architects define correctness contracts at each level.

Level 1 — Schema correctness
Does the data have the right shape? Correct column names, data types, nullability constraints. How you enforce it: Delta Lake schema enforcement (mergeSchema=false for strict mode), Great Expectations schema validation, Auto Loader schema inference with drift alerts. Failure action: quarantine to a dead-letter zone, alert, do not propagate.
Level 2 — Completeness correctness
Is all expected data present? No missing rows, no truncated files, no partial loads. How you enforce it: Row count validation between source and target after each pipeline run. Checksum or hash comparison for critical tables. Watermark tracking — if yesterday's batch delivered 1M rows and today's delivers 50K, trigger an alert before loading Gold. This is especially critical for financial data.
Level 3 — Referential correctness
Do foreign keys resolve? Do fact table keys exist in dimension tables? How you enforce it: Referential integrity checks in Great Expectations or dbt tests. In Databricks, a custom PySpark check: anti-join between fact and dimension — any orphaned fact rows get flagged and routed to a quarantine table with the reason logged.
Level 4 — Business rule correctness
Does data conform to domain logic? Order amount cannot be negative. Transaction date cannot be in the future. Customer age must be between 0-120. How you enforce it: Business rule engine in Silver transformation — parameterised rule configs (so business teams can update rules without code changes), failed records to quarantine with rule violation logged, metrics dashboard showing violation rates over time.
Level 5 — Consistency correctness
Is the same fact reported identically across all systems? The total revenue in the finance dashboard must match the sales dashboard must match the data warehouse. How you enforce it: Conformed dimensions and conformed metrics — single definitions of revenue, customer, and product agreed across business domains and enforced at the Gold layer. Metric store (e.g. dbt metrics) ensures one definition, many consumers.

Data quality SLA framework — how architects define it

Timeliness SLA
Data must be available in Gold layer within X minutes/hours of source system update. Define per domain: operational data = 15 min, financial reporting = 4 hours, historical analytics = next day. Monitor with pipeline duration alerting.
Completeness SLA
95% of expected records must arrive within the SLA window. 99% within 2x the window. Define acceptable late-arrival tolerance per domain. Track with daily completeness scorecards.
Accuracy SLA
Less than 0.01% of records may fail business rule validation. Any breach triggers automated rollback of the affected batch and incident creation. Critical financial data may require 100% accuracy — zero tolerance.
Your Kahramaa story: "At Kahramaa I implemented a data quality framework across all three layers. At Bronze, schema validation on ingestion. At Silver, Great Expectations checks for completeness, referential integrity, and value range validation — failed records were quarantined to a dead-letter table rather than propagating to Gold. At Gold, we ran cross-system reconciliation reports daily — the Power BI consumption layer numbers had to reconcile with the source Oracle system within 0.01%. Unity Catalog lineage meant when a discrepancy was found, we could trace it to the exact pipeline run and source record within minutes."

Replay-safe ingestion — idempotency & deduplication

Critical for production-grade pipelines — this is where senior engineers separate from architects

What is idempotency and why does it matter?

An operation is idempotent if running it multiple times produces the same result as running it once. In data pipelines: if a pipeline runs twice due to a failure and retry, the target table should look exactly the same as if it ran once. Without idempotency, retries cause duplicate records, double-counted metrics, and corrupted aggregations.

Three levels of idempotency in your architecture

Level 1 — Idempotent writes (Delta Lake MERGE)
The most important technique. Instead of INSERT (which duplicates on retry), use MERGE INTO — match on a natural/surrogate key, UPDATE if exists, INSERT if new. Delta Lake's MERGE is ACID — it either fully succeeds or fully rolls back.

Your experience: You implemented this at Kyndryl for SCD2 — MERGE INTO on the dimension table matching on device_id + is_current, closing old rows and inserting new ones. If the pipeline retried, the MERGE was idempotent — same result every time.
-- Idempotent SCD2 MERGE in Delta Lake (from your Kyndryl work) MERGE INTO silver.dim_network_device AS target USING ( SELECT device_id, config_hash, config_state, current_timestamp() AS effective_from FROM bronze.network_changes_staging WHERE batch_id = '2025-03-25-001' -- deterministic batch key ) AS source ON target.device_id = source.device_id AND target.is_current = true WHEN MATCHED AND target.config_hash != source.config_hash THEN UPDATE SET target.is_current = false, target.effective_to = source.effective_from WHEN NOT MATCHED THEN INSERT (device_id, config_hash, config_state, effective_from, effective_to, is_current) VALUES (source.device_id, source.config_hash, source.config_state, source.effective_from, '9999-12-31', true)
Level 2 — Deterministic batch keys
Every pipeline run must have a unique, deterministic batch_id — typically the processing date + sequence number. This batch_id is written to every record. On retry, the pipeline first deletes records with that batch_id (or uses MERGE), then re-inserts. Because the batch_id is the same on retry, the result is identical to the first run.

Anti-pattern: Using current_timestamp() as a pipeline run ID — every retry generates a new ID, making deduplication impossible.
Level 3 — Checkpoint-based resumption
For streaming pipelines, Databricks Structured Streaming uses checkpoints to track exactly which offsets have been processed. On restart, it resumes from the last committed checkpoint — not from the beginning, not from "now". This is the streaming equivalent of idempotency — exactly-once processing semantics with Delta Lake as the sink.

Your Kyndryl work: Your Event Hubs + Structured Streaming pipeline used checkpoints stored in ADLS. When a node failed, the stream restarted from the last checkpoint — no data loss, no duplicates.

Deduplication strategies

"How do you handle duplicate records in a high-volume ingestion pipeline?"
"Deduplication strategy depends on where duplicates originate and what the volume is.

Source-level duplicates (same event sent multiple times by the source): I assign a deterministic event_id at ingestion — typically a hash of the key business fields (source_system + entity_id + event_timestamp). At Bronze I log all records including duplicates. At Silver, I deduplicate using ROW_NUMBER() OVER (PARTITION BY event_id ORDER BY ingestion_timestamp DESC) = 1 — keeping the latest version of each event_id.

Pipeline retry duplicates (retry after failure re-processes the same batch): Handled by idempotent MERGE writes at Silver and Gold — the natural key match ensures existing records are updated, not duplicated.

Streaming deduplication: Databricks Structured Streaming with dropDuplicates(['event_id']) within a watermark window. This maintains a state store of seen event_ids within the window. Beyond the window, Delta Lake's MERGE handles any late-arriving duplicates.

At scale — say 100M events/day — full in-memory deduplication is expensive. I use a bloom filter approach: fast probabilistic check first (is this event_id likely seen?), only query the state store on positive hits. This reduces state store lookups by 95%+ for typical duplicate rates."
# Deduplication in PySpark Structured Streaming (your Kyndryl pattern) from pyspark.sql import functions as F deduplicated_stream = ( raw_stream .withWatermark("event_timestamp", "2 hours") # late arrival tolerance .dropDuplicates(["event_id", "event_timestamp"]) # within watermark window ) # Write with exactly-once semantics to Delta Lake query = ( deduplicated_stream.writeStream .format("delta") .outputMode("append") .option("checkpointLocation", "/mnt/checkpoints/network_events") .trigger(processingTime="30 seconds") .start("/mnt/silver/network_events") )

Watermarking, late-arriving & out-of-order data

The hardest streaming problem — and one most engineers get wrong

Event time vs processing time — the core concept

Event time what happened when
The timestamp when the event actually occurred in the real world. An IoT sensor reading at 14:32:05. A transaction completed at 09:15:22. This is what you want to aggregate on for correct analytics.
Processing time when we saw it
When the event arrived at the pipeline. Always later than event time — due to network latency, device offline time, retry delays. Processing-time windows are simple but give wrong results for late data.
The problem: An IoT device goes offline at 14:30 and reconnects at 16:00, sending all buffered events. At 16:00, your pipeline receives events with timestamps from 14:30–16:00. If you've already closed the 14:30–15:00 aggregation window, do you reopen it? For how long? This is exactly the problem watermarking solves.

Watermarking — the architecture decision

A watermark is a threshold that defines how late data can arrive and still be included in a window. It tells the engine: "I will wait up to X minutes for late data. After that, I close the window and emit the result."

withWatermark("event_timestamp", "2 hours") means: the current window stays open until the max event_timestamp seen so far minus 2 hours. Any event arriving after this threshold is either discarded or routed to a late-arrival correction path.
"How do you design a system to handle late-arriving and out-of-order events?"
"I design a two-path system: the primary streaming path and a late-arrival correction path.

Primary path — streaming with watermark: I configure watermarks based on the observed late-arrival distribution of each source. For Kahramaa IoT devices, I measured that 99% of events arrived within 30 minutes of event time. So I set a 45-minute watermark — covering 99th percentile with buffer. This keeps state store memory bounded while tolerating almost all late arrivals.

Watermark setting strategy: Don't guess — measure. Run a historical analysis: MAX(processing_time - event_time) grouped by source and hour of day. Set watermark at P99 of that distribution. Review monthly as source behaviour changes.

Late-arrival correction path: Events arriving after the watermark are not discarded — they're routed to a late_arrival_staging table. A daily batch job (running at 2 AM) replays these events against the affected Delta Lake partitions using a MERGE, correcting the historical aggregations. Delta Lake time travel means the pre-correction state is preserved for audit.

Out-of-order handling: Structured Streaming processes events in arrival order but attributes them to the correct event-time window. Z-order indexing on event_timestamp in Delta Lake means retroactive corrections only scan the relevant partition — no full table scan needed.

At Kyndryl, this pattern handled NAB's weekend change window backlog — thousands of network events arriving Monday morning with Friday timestamps — without corrupting the Saturday/Sunday operational metrics."
# Two-path late arrival architecture (your pattern, articulated) # Path 1: Primary streaming with watermark windowed_agg = ( stream .withWatermark("event_time", "45 minutes") .groupBy( F.window("event_time", "15 minutes"), "device_id" ) .agg(F.count("*").alias("event_count"), F.avg("metric_value").alias("avg_metric")) ) # Path 2: Route truly late events to staging late_events = ( stream .filter(F.col("event_time") < F.current_timestamp() - F.expr("INTERVAL 45 MINUTES")) .writeStream.format("delta") .option("checkpointLocation", "/chk/late_staging") .start("/mnt/silver/late_arrival_staging") ) # Nightly correction job: MERGE late events into final aggregation table # Delta time travel preserves pre-correction state for audit

Watermark trade-off — what architects must articulate

Longer watermark window
  • More late events included automatically
  • Higher result accuracy
  • Better for devices with long offline periods
Cost of longer window
  • Larger state store in memory
  • Higher latency to emit results
  • More cluster memory needed
Architect answer: "The watermark is fundamentally a latency-accuracy trade-off. I set it based on SLA requirements — if the business needs real-time fraud signals within 30 seconds, I cannot afford a 2-hour watermark. Instead I use a shorter watermark for the real-time path and a late-arrival correction job for accuracy. If the business needs correct historical aggregations above all else, I use a longer watermark and accept higher latency. I always make this trade-off explicitly, with the business, documented in the architecture decision record."

Streaming architecture — fraud detection & real-time transaction processing

Low-latency, fault-tolerant streaming design — the kind asked in architect interviews

Real-time fraud detection architecture — full design

"Design a low-latency streaming architecture for real-time fraud detection signals."
"I'd design this as a three-tier streaming architecture: ingestion, enrichment, and decisioning — each with different latency and durability requirements.

Tier 1 — Ingestion (sub-100ms): Transactions arrive via Azure Event Hubs with 32 partitions (scaled to throughput). Event Hubs provides durable, ordered, replayable ingestion with consumer group isolation — the fraud detection consumer reads independently from the analytics consumer. Partition key = account_id, ensuring all transactions for the same account land in the same partition and are processed in order.

Tier 2 — Enrichment (100ms-500ms): Databricks Structured Streaming reads from Event Hubs. For each transaction, enrich with: (a) customer profile from Delta Live Tables (pre-materialised, cached); (b) account velocity features — transaction count, total amount, unique merchants in last 1/5/60 minutes, computed using stateful streaming with watermark; (c) device fingerprint from a Redis cache (sub-millisecond lookup).

Tier 3 — Decisioning (500ms-1s total): Enriched event passed to a Databricks MLflow-served model (pre-loaded in memory, not loaded per request). Model scores the transaction — high score triggers real-time alert to downstream systems via Event Hubs output topic. Low score routes to Delta Lake for batch review.

Fault tolerance: Every tier has checkpointing. If Tier 2 fails, it restarts from the last Event Hubs offset checkpoint — no data loss, no reprocessing from the beginning. The stateful velocity features are stored in a RocksDB state store on the worker — on restart, state is restored from the checkpoint.

Latency budget breakdown: Event Hubs ingestion 10ms + Structured Streaming micro-batch 30s is too slow for fraud. So I configure trigger(continuous='100 milliseconds') for the fraud path — Databricks Continuous Processing mode — giving true low-latency streaming, not micro-batches."

Auto Loader — efficient ingestion for continuously arriving files

"Files are continuously arriving in ADLS. Design an efficient ingestion system."
"The naive approach — schedule an ADF pipeline every 5 minutes to scan the folder — doesn't scale. At high file volumes, directory listing becomes expensive and you risk processing the same file twice or missing files between scans.

The right approach is Databricks Auto Loader with Azure Event Grid notifications.

Auto Loader subscribes to Event Grid file creation events from ADLS — instead of polling the directory, it gets a notification the instant a file lands. This scales to millions of files with no directory listing overhead.

Key configurations I use:
- cloudFiles.schemaLocation: Auto Loader infers schema from first files and stores it. If new files have extra columns (schema drift), it merges the schema automatically rather than failing — new columns appear as nulls in historical data.
- cloudFiles.inferColumnTypes=true: Infers correct types rather than defaulting everything to string.
- cloudFiles.maxFilesPerTrigger: Throttle file ingestion rate to prevent overwhelming downstream Silver transformations.

Idempotency: Auto Loader tracks which files have been processed in a RocksDB checkpoint. Restarting the stream never re-processes already-ingested files — exactly-once file ingestion.

At Empower Retirement, I used this exact pattern to replace a scheduled ADF pipeline that was missing files during high-volume periods. Auto Loader handled the backlog during peak and maintained sub-5-minute file-to-Bronze latency consistently."

Fault-tolerant, scalable pipeline design

High-volume transaction data — the design decisions that matter at scale

The 5 pillars of fault-tolerant data pipeline design

Pillar 1 — Idempotent writes already covered
MERGE over INSERT. Deterministic batch keys. Every retry produces the same result. Never use mutable state that doesn't survive a restart.
Pillar 2 — Checkpointing & resumption
Batch: Track the last successfully processed watermark (max processed timestamp or batch_id) in a metadata table. On restart, read this watermark and process only new data. Never re-scan from the beginning of time.

Streaming: Databricks Structured Streaming checkpoints to ADLS automatically. Checkpoint = committed offsets + state store snapshot. Restart is exactly from the last committed state — not from "latest" (which would miss events) and not from "earliest" (which would reprocess everything).
Pillar 3 — Dead-letter queue pattern
Never fail the whole pipeline because of one bad record. Route malformed, schema-violating, or business-rule-failing records to a dead-letter Delta table with: original payload, failure reason, pipeline run ID, timestamp. A separate alerting job monitors the dead-letter table — if dead-letter rate exceeds threshold (e.g. 0.1%), trigger incident.

Architecture benefit: The main pipeline continues processing good records while bad records are investigated separately. In financial systems this is critical — a single corrupt record should not halt transaction processing.
Pillar 4 — Backpressure management
When the source produces faster than the sink can consume, the pipeline must not crash — it must slow down gracefully.

For Structured Streaming: maxOffsetsPerTrigger limits how many Event Hubs messages are read per micro-batch. If downstream is slow, the trigger waits — the messages sit safely in Event Hubs (durable, replayable) rather than overwhelming the processing cluster.

For batch: ADF concurrency limits on pipeline activities. Databricks job cluster auto-scaling — adds workers when queue depth grows, scales down during idle.
Pillar 5 — Circuit breaker pattern
If a downstream system (Gold layer, API, downstream pipeline) is consistently failing, stop sending data to it rather than building up a backlog of failed writes. Define: failure threshold (e.g. 5 consecutive failures), open state (stop sending, route to staging), half-open state (test with one record), closed state (resume normal flow).

In practice implemented as a pipeline health metadata table — each pipeline writes its status. Downstream pipelines read their dependency's status before running. If upstream is in circuit-open state, downstream waits rather than processing on stale data.

High-volume transaction data — specific design patterns

"Design a fault-tolerant, scalable pipeline for 10 billion transactions per day."
"At 10B transactions/day that's roughly 115,000 transactions per second on average, with likely 10x peaks during business hours — up to 1M TPS at peak.

Ingestion layer: Azure Event Hubs with 100 partitions (scale unit). Partition key = account_id for ordering guarantees per account. Event Hubs retains events for 7 days — this is the replay buffer for any downstream failure.

Bronze landing: Auto Loader consuming from Event Hubs, writing to Delta Lake partitioned by date and hour. Trigger every 30 seconds. At 1M TPS peak, each micro-batch processes ~30M events — Databricks cluster of 20 workers (16 vCPU each) handles this comfortably with Spark's parallel partition processing.

Silver transformation: Separate cluster from Bronze — compute isolation prevents ingestion from competing with transformation. Silver runs every 5 minutes, processes the last completed Bronze hour partitions. MERGE for SCD2 dimension updates, INSERT OVERWRITE for fact partitions (idempotent — overwrites the same partition on retry).

Partition strategy: Fact table partitioned by transaction_date + transaction_hour. Z-order on account_id and merchant_id. This means a fraud analyst querying "all transactions for account X in the last 24 hours" scans at most 24 hourly partitions, Z-order filtered to that account — not 10B rows.

Monitoring: Azure Monitor alerts on: Event Hubs consumer lag (are we keeping up?), Bronze pipeline duration (degrading over time?), dead-letter rate (data quality degrading?), Silver MERGE duration (dimension growth slowing merges?)."

Compaction vs freshness SLA — the architect's trade-off

One of the most nuanced Delta Lake topics — shows deep operational understanding

Why this trade-off exists

Delta Lake uses an append-only transaction log. Every streaming micro-batch or small file write creates a new Parquet file. After 1 day of 30-second micro-batches, you have 2,880 small files for that partition. Reading that partition requires opening 2,880 files — massive overhead. Compaction (OPTIMIZE) merges these into fewer, larger files — dramatically improving read performance. But OPTIMIZE rewrites the partition files, which takes time and blocks concurrent writes on that partition.
"How do you balance compaction with freshness SLAs in a streaming Delta Lake pipeline?"
"This is a core operational decision I've made explicitly in production. The tension is: OPTIMIZE improves read performance but creates a write-pause on the partition being compacted — during which, new streaming micro-batches either queue or skip that partition.

Strategy 1 — Time-window OPTIMIZE (my primary approach):
Run OPTIMIZE only on partitions that are no longer receiving active streaming writes. For hourly partitions, the previous day's partitions are 'cold' — no new streaming data will arrive. Schedule OPTIMIZE on cold partitions at 2 AM daily. Current and previous hour partitions are never compacted during business hours — they're small-file-fragmented but that's acceptable because freshness SLA is paramount for those partitions.

Strategy 2 — Separate read-optimised copy:
For high-concurrency read workloads (fraud analysts, real-time dashboards), maintain a second Delta table that is compacted — a clone of the streaming table, compacted every 15 minutes on a rolling basis. Streaming writes go to the primary table. Reads go to the compacted copy, which may be 15 minutes stale. Acceptable if the freshness SLA allows it.

Strategy 3 — Delta Lake liquid clustering (modern approach):
In newer Delta Lake versions, liquid clustering replaces both partitioning and Z-order with an incremental clustering approach that runs in the background without blocking writes. This eliminates the compaction-freshness trade-off for most cases — I advocate moving to this for new pipelines.

VACUUM consideration: VACUUM removes old file versions beyond the retention period. Never run VACUUM with a retention period shorter than your longest running query — a query that started before VACUUM runs may reference file versions that VACUUM just deleted, causing FileNotFoundException. I set retention to 7 days minimum and alert if any query runs longer than 6 hours."

The full compaction configuration I use in production

# Strategy 1: Targeted OPTIMIZE on cold partitions only from delta.tables import DeltaTable from datetime import datetime, timedelta cold_date = (datetime.now() - timedelta(days=1)).strftime("%Y-%m-%d") # Only optimize yesterday's partitions - never touch today's (streaming active) DeltaTable.forPath(spark, "/mnt/silver/transactions") \ .optimize() \ .where(f"transaction_date = '{cold_date}'") \ .executeZOrderBy("account_id", "merchant_id") # Auto-compact for active streaming partitions (smaller benefit, zero blocking) spark.conf.set("spark.databricks.delta.autoCompact.enabled", "true") spark.conf.set("spark.databricks.delta.autoCompact.minNumFiles", "50") # VACUUM with safe retention window spark.sql(""" VACUUM delta.`/mnt/silver/transactions` RETAIN 168 HOURS -- 7 days minimum, never shorter than longest query runtime """)
Compacting aggressively
  • Fewer files, faster reads
  • Lower storage costs (fewer small files)
  • Better BI dashboard query speed
Risk of aggressive compaction
  • Write-pause during OPTIMIZE
  • Streaming freshness degraded
  • VACUUM too short = query failures
  • Rewrite cost on large partitions
Architect answer that shows mastery: "The compaction-freshness trade-off is ultimately a SLA negotiation. I sit with the business and ask two questions: what's the maximum query latency they'll accept for historical data (drives how aggressively I compact cold partitions), and what's the maximum acceptable data age for operational dashboards (drives how aggressively I can compact recent partitions). Once those are documented, the compaction schedule follows automatically. I never make this decision unilaterally as a technical choice — it's a business SLA decision with technical implementation."

Quick-fire technical answers — memorise these

"What's the difference between exactly-once and at-least-once semantics?"
At-least-once: Every event is processed, but may be processed more than once on retry. Requires idempotent writes to be safe. Easier to implement, higher throughput.
Exactly-once: Every event processed exactly once — no duplicates, no loss. Structured Streaming + Delta Lake provides this via checkpointing + ACID transactions. Slight performance overhead. Use for financial transactions where duplicate processing = double charge.
"What is CDC and how do you implement it?"
Change Data Capture — capturing only the rows that changed in a source system, not full table dumps. Implementation options: (1) Database log-based CDC (Debezium reads Oracle redo log — lowest source impact, sub-second latency); (2) Timestamp-based CDC (query WHERE updated_at > last_watermark — simple but misses hard deletes); (3) Hash-based CDC (compute row hash, compare with previous run — detects all changes but full scan needed). At Kahramaa I used timestamp-based CDC for Oracle with a high-watermark pattern, and Delta Lake MERGE for applying changes. At Kyndryl I implemented CDC watermarking for the streaming network telemetry path.
"How do you handle schema evolution in a production pipeline?"
Three scenarios: (1) New column added — Auto Loader with mergeSchema=true handles automatically, new column appears with nulls in historical data; (2) Column renamed — breaking change, requires pipeline versioning and a migration script; (3) Column type changed (e.g. int to string) — Delta Lake rejects by default, requires explicit schema override. My approach: schema changes are events, treated like code changes — reviewed, versioned, tested in lower environments before production. Unity Catalog schema versioning tracks history.
"What is data lineage and why does it matter architecturally?"
Data lineage tracks the complete journey of a data element — from source system through every transformation to every consumption point. Architecturally it matters for: (1) Impact analysis — if an Oracle column changes, lineage tells you every dashboard and ML model that will break; (2) Incident root cause — when a Gold layer metric is wrong, lineage traces it to the exact pipeline and source record; (3) Compliance — GDPR right-to-erasure requires knowing everywhere a customer's data exists — lineage makes this tractable. I implemented end-to-end lineage using Unity Catalog at Kahramaa and Azure Purview at Kyndryl.
